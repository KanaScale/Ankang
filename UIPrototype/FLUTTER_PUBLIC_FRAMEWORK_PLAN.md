# 安康助手 Flutter 公共框架工作规划文档

## 1. 文档说明

本文档用于规划“安康助手”项目中 Flutter 前端公共框架部分的建设工作，明确公共框架负责人的任务范围、目标、交付内容和实施顺序，为后续登录、首页、健康数据、提醒、SOS 等业务模块开发提供统一基础。

公共框架不是单独的业务功能，而是整个 Flutter 前端的“底层支撑层”。其质量会直接影响后续多人协作效率、代码规范程度、接口联调成本以及最终项目的稳定性。

---

## 2. 公共框架建设目标

公共框架建设的核心目标如下：

- 搭建统一、清晰、可扩展的 Flutter 项目结构
- 提供可复用的网络请求能力和 token 管理能力
- 提供统一的页面路由、全局主题和通用组件
- 降低后续业务模块开发的重复工作
- 减少多人协作时的目录混乱和代码冲突
- 为后续接口联调、功能测试和答辩演示提供稳定基础

---

## 3. 公共框架负责人的定位

公共框架负责人主要负责“基础设施建设”，不是负责某一个业务页面，而是负责让其他成员能够在一个统一规范的 Flutter 工程中高效开发。

可以将该角色理解为前端项目的基础架构负责人，其工作重点包括：

- 项目初始化
- 目录结构设计
- 全局配置管理
- 网络请求封装
- 登录态管理
- 通用组件沉淀
- 页面开发规范约定

---

## 4. 工作范围

## 4.1 应负责的内容

- Flutter 项目初始化与依赖配置
- `lib` 目录的整体组织方式
- 路由管理机制
- API 基础地址和环境配置
- HTTP 请求封装
- token 存储、读取、清除与自动携带
- 全局主题、颜色、文字风格和按钮风格
- 通用组件封装
- 基础工具类封装
- 页面开发模板和示例代码

## 4.2 原则上不负责的内容

- 登录页具体业务逻辑细节
- 首页业务布局细节
- 健康数据录入和趋势图具体业务实现
- 提醒、联系人、SOS 页面具体业务实现

说明：

- 公共框架负责人可以先提供这些页面的空壳或示例模板
- 但完整业务页面应由对应业务负责人继续实现

## 6. 核心工作拆分

## 6.1 项目初始化

### 工作内容

- 创建 Flutter 项目
- 配置 Android 运行端
- 配置必要依赖
- 保证项目可在组内统一运行

### 建议依赖

- `dio` 或 `http`：网络请求
- `flutter_secure_storage`：安全保存 token
- `fl_chart`：趋势图展示
- `provider`、`riverpod` 或团队统一采用的状态管理方案

### 交付结果

- 项目可以正常启动
- 基础依赖安装完成
- 其他成员拉取代码后可直接运行

---

## 6.2 全局配置设计

### 工作内容

- 配置 API 基础地址
- 配置应用名称、版本号、环境信息
- 配置开发环境和联调环境切换方式

### 建议文件

- `config/api_config.dart`
- `config/app_config.dart`

### 示例职责

- `api_config.dart`：统一定义 `baseUrl`
- `app_config.dart`：定义应用名称、默认分页大小、请求超时时间等

### 交付结果

- 后续成员无需在多个文件中手动写接口地址
- 支持统一修改服务端地址

---

## 6.3 路由与页面导航机制

### 工作内容

- 设计页面跳转方式
- 管理页面路由名称
- 提供统一的页面注册入口

### 建议文件

- `routes/app_routes.dart`
- `app.dart`

### 设计要求

- 登录页、首页、健康记录页、提醒页、SOS 页等都应提前约定路由名
- 路由名称统一使用常量，避免字符串硬编码

### 交付结果

- 页面跳转方式统一
- 首页负责人和各业务负责人可以直接接入既定路由

---

## 6.4 网络请求层封装

### 工作内容

- 封装统一的 HTTP 请求工具
- 处理 GET、POST、PUT、DELETE 请求
- 统一超时、异常、错误码处理
- 统一添加请求头

### 建议文件

- `services/api_client.dart`

### 设计要求

- 支持基础请求方法
- 支持自动拼接 `baseUrl`
- 支持统一返回结果解析
- 支持拦截器打印请求日志
- 支持统一处理 401、403、500 等错误

### 建议能力

- 自动携带 `Authorization: Bearer <token>`
- token 失效时自动触发登录失效处理
- 提供统一的成功和失败数据模型

### 交付结果

- 其他成员只需写业务接口方法，不需要重复封装底层请求逻辑

---

## 6.5 token 与登录态管理

### 工作内容

- 封装 token 的保存、读取、删除
- 实现登录后持久化保存
- 实现退出登录后的清理逻辑

### 建议文件

- `utils/token_storage.dart`

### 设计要求

- 使用 `flutter_secure_storage` 保存 token
- 对外提供简单方法，例如：
  - `saveToken`
  - `getToken`
  - `clearToken`

### 交付结果

- 登录模块负责人可直接调用 token 工具
- 所有接口可统一从本地读取 token

---

## 6.6 数据模型与统一响应结构

### 工作内容

- 设计前端通用响应模型
- 定义核心业务实体的基础模型结构

### 建议文件

- `models/base_response.dart`
- `models/user_model.dart`
- `models/health_record_model.dart`
- `models/reminder_model.dart`
- `models/emergency_contact_model.dart`

### 设计要求

- 支持 JSON 序列化与反序列化
- 字段命名与后端接口保持一致或统一转换
- 避免页面层直接操作原始 Map 数据

### 交付结果

- 业务负责人可直接使用已有模型对象开发页面

---

## 6.7 全局主题与样式规范

### 工作内容

- 统一全局颜色
- 统一按钮风格
- 统一输入框样式
- 统一标题文字和正文文字风格

### 建议文件

- `config/theme_config.dart`

### 设计要求

- 首页、图表页、提醒页、SOS 页保持统一视觉风格
- 按钮、输入框、卡片圆角和留白尽量统一
- 考虑老人用户使用习惯，字体与点击区域应适当偏大

### 交付结果

- 业务页面视觉风格统一
- 后续成员开发时无需重复定义样式

---

## 6.8 通用组件封装

### 工作内容

- 封装常用 UI 组件
- 抽取业务模块可能重复使用的视图

### 优先级较高的组件

- 通用按钮 `CommonButton`
- 通用输入框 `CommonInput`
- 通用卡片 `CommonCard`
- 列表空状态组件 `EmptyView`
- 加载中组件 `LoadingView`
- 错误展示组件 `ErrorView`
- 页面标题栏或通用 Section 头部组件

### 交付结果

- 登录、记录、提醒、SOS 等页面可共享同一套基础组件
- 降低后续页面样式不一致问题

---

## 6.9 工具类与基础能力

### 工作内容

- 日期格式化工具
- 表单校验工具
- 常量管理
- 提示信息封装

### 建议文件

- `utils/date_util.dart`
- `utils/validator_util.dart`
- `utils/constants.dart`
- `utils/toast_util.dart`

### 交付结果

## 6.10 页面模板与开发示例

### 工作内容

- 提供一个标准页面模板
- 提供一个标准 Service 调用示例
- 提供一个标准 Model 解析示例

### 模板内容建议

- 页面结构模板
- 请求发起模板
- 列表展示模板
- 加载状态与异常状态模板

### 交付结果

- 业务负责人可以按统一模板快速开始开发
- 降低代码风格不一致问题

## 7. 推荐开发顺序

为避免后续开发阻塞，建议公共框架工作按以下顺序推进：

### 第一阶段：搭建最小可运行框架

- 创建 Flutter 工程
- 配置依赖
- 设计目录结构
- 完成 `main.dart` 与 `app.dart`
- 完成基础路由配置

### 第二阶段：完成底层核心能力

- 完成 `ApiClient`
- 完成 `token_storage`
- 完成基础配置文件
- 完成统一响应模型

### 第三阶段：完成通用 UI 能力

- 完成全局主题
- 完成按钮、输入框、空状态、加载态等通用组件

### 第四阶段：提供业务接入模板

- 提供登录示例调用
- 提供列表页示例结构
- 提供页面跳转示例

说明：

- 第一、二阶段完成后，其他业务成员即可开始并行开发
- 第三、四阶段可以边支持业务边逐步完善

## 9. 代码规范建议

为了方便后续开发，公共框架负责人应在文档或代码中统一以下规范：

### 9.1 命名规范

- 页面文件：`xxx_page.dart`
- 服务文件：`xxx_service.dart`
- 模型文件：`xxx_model.dart`
- 工具文件：`xxx_util.dart`
- 组件文件：按组件名命名，如 `common_button.dart`

### 9.2 目录使用规范

- 页面逻辑放在 `pages`
- 网络请求放在 `services`
- 数据结构放在 `models`
- 通用 UI 放在 `widgets`
- 工具函数放在 `utils`

### 9.3 编码规范

- 页面不直接写底层请求逻辑
- 页面不直接解析原始 JSON Map
- 统一使用已有组件和主题
- 提交前保持代码格式统一

## 11. 验收标准

公共框架工作是否完成，可以按以下标准进行验收：

### 11.1 基础运行验收

- 项目可以正常运行到首页或登录页
- 新成员拉取代码后可以快速启动项目

### 11.2 架构验收

- 目录结构清晰
- 路由配置完整
- 网络层、模型层、页面层职责分离

### 11.3 复用性验收

- 其他成员可基于现有框架快速新增页面
- 通用组件可直接复用
- token 与请求逻辑不需要每个模块重复开发

### 11.4 联调支撑验收

- 登录接口能够接入
- 业务接口能够通过统一请求层发起
- token 能自动携带
- 异常提示机制基本可用

## 12. 风险点与应对措施

### 12.1 框架过度设计

风险说明：

- 如果前期封装过重，会拖慢整体进度

应对措施：

- 先实现最小可用框架
- 优先保证能支撑业务开发，再逐步完善抽象

### 12.2 公共组件过少

风险说明：

- 如果不提前沉淀通用组件，后续页面风格会不统一

应对措施：

- 至少优先抽取按钮、输入框、卡片、加载态、空状态五类组件

### 12.3 请求层设计不统一

风险说明：

- 不同成员各自发请求，会导致风格混乱、错误处理不一致

应对措施：

- 所有网络请求统一走 `ApiClient`
- 所有接口文件统一放入 `services`

### 12.4 token 管理混乱

风险说明：

- 如果 token 保存与读取逻辑分散在多个页面，会增加 bug 风险

应对措施：

- token 统一封装在 `utils/token_storage.dart`
- 统一由请求拦截器自动读取并携带

## 13. 后续建议

为了让公共框架更好服务后续开发，建议公共框架负责人在完成基础工作后继续承担以下协调职责：

- 维护公共组件和工具类
- 审查是否有重复造轮子的代码
- 协助业务负责人解决路由、样式、接口调用问题
- 在联调阶段统一修复公共层问题

---

## 14. 总结

Flutter 公共框架工作是整个前端开发的基础。只要公共框架设计合理、目录清晰、网络层统一、主题和组件规范，后续登录首页、健康数据、提醒和 SOS 等模块都可以更顺畅地并行开发。

因此，公共框架负责人的核心价值不在于页面数量，而在于为团队建立统一的开发底座。该工作完成得越扎实，后续开发成本越低，协作效率越高，也越有利于课程项目按时完成并形成较好的最终展示效果。
