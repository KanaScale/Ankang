# 安康助手 Flutter 前端工作划分文档

## 1. 文档说明

本文档用于明确“安康助手”项目中 Flutter 前端部分的人员分工、模块边界、协作方式和阶段安排，便于团队成员并行开发、减少冲突、提高联调效率。

本次前端开发按 4 人小组进行划分，采用“公共框架 + 业务模块”方式组织任务：

- 1 人负责公共框架与通用能力建设
- 1 人负责登录模块与首页模块
- 1 人负责健康数据录入、历史记录与趋势图表
- 1 人负责提醒模块与 SOS 紧急求助模块

如后续团队成员有具体姓名，可将本文档中的“成员 A、成员 B、成员 C、成员 D”替换为实际人员姓名。

---

## 2. 分工目标

本次分工的核心目标如下：

- 保证 4 名成员都能承担相对独立且完整的前端任务
- 将公共能力统一收口，避免重复造轮子
- 将页面开发与接口联调拆分清楚，降低合并冲突
- 保证最终可以形成一套可演示、可答辩、可交付的 Flutter Android App

---

## 3. 分工原则

### 3.1 模块边界清晰

- 公共框架负责人优先完成项目骨架、路由、网络请求、通用组件和基础工具
- 业务模块负责人基于统一框架开发具体页面和功能
- 各成员尽量只修改自己负责目录下的主要文件

### 3.2 接口统一

- 所有业务页面统一通过 `services` 层调用后端 API
- 所有数据结构统一通过 `models` 层定义
- 页面不直接拼接原始请求逻辑，避免重复代码

### 3.3 组件复用

- 通用按钮、输入框、卡片、图表容器、空状态组件由公共框架负责人统一整理
- 业务负责人优先复用已有组件，不重复创建同类基础控件

### 3.4 先框架后业务

- 先完成项目初始化、目录结构、基础网络层和页面路由
- 再分别并行开发登录首页、健康数据、提醒 SOS 等业务页面

## 4. 总体工作划分

| 成员 | 负责方向 | 核心内容 | 主要交付结果 |
|---|---|---|---|
| 成员 A | 公共框架 | 项目初始化、目录结构、路由、主题、网络层、token 管理、通用组件 | 可供其他成员直接开发的 Flutter 基础框架 |
| 成员 B | 登录与首页 | 登录页、注册页、首页布局、用户信息展示、快捷入口 | 用户能够完成登录并进入首页 |
| 成员 C | 健康数据与图表 | 健康数据录入、历史记录列表、趋势图页面、图表展示 | 能录入血压血糖等数据并查看趋势分析 |
| 成员 D | 提醒与 SOS | 提醒管理、紧急联系人、SOS 页面、紧急求助入口 | 能设置提醒并完成一键求助流程展示 |

## 6. 具体人员分工

## 6.1 成员 A：公共框架负责人

### 6.1.1 主要职责

- 搭建 Flutter 项目基础结构
- 统一目录划分
- 配置全局主题、颜色、字体、按钮样式
- 配置命名路由或页面跳转机制
- 封装网络请求层
- 封装 token 存储与自动携带
- 封装基础通用组件
- 制定前端代码规范与命名规范

### 6.1.2 建议负责目录

```text
lib/
├── main.dart
├── app.dart
├── config/
├── services/api_client.dart
├── utils/
├── widgets/common/
└── 部分 models 公共基类或通用响应封装
```

### 6.1.3 详细任务

1. 项目初始化

- 创建 Flutter 工程
- 配置 Android 运行环境
- 引入基础依赖，例如网络请求库、图表库、本地存储库

2. 公共框架搭建

- 搭建 `models`、`services`、`pages`、`widgets`、`utils` 基础目录
- 约定页面命名、模型命名、服务命名方式

3. 网络层封装

- 封装统一请求类 `ApiClient`
- 支持 GET、POST、PUT、DELETE 请求
- 支持统一异常处理
- 支持自动注入 JWT 到请求头

4. 本地存储与登录态管理

- 封装 token 存储读取删除逻辑
- 支持登录后保存 token
- 支持退出登录清空 token

5. 通用 UI 组件

- 公共按钮组件
- 公共输入框组件
- 公共卡片组件
- 加载中组件
- 空状态组件
- 错误提示组件

6. 协作支持

- 为其他成员提供统一的页面模板
- 提供接口调用示例
- 提供基础假数据页面壳子，便于并行开发

### 6.1.4 交付结果

- 可以运行的 Flutter 工程骨架
- 通用目录结构
- 公共网络请求封装
- token 管理工具
- 基础通用组件
- 开发规范说明

### 6.1.5 与其他成员的协作边界

- 不负责具体业务页面细节实现
- 但需要提供业务页面开发所需的底层支持
- 其他成员如果需要新增公共组件，应优先与成员 A 协调后统一放入公共目录

## 6.2 成员 B：登录与首页负责人

### 6.2.1 主要职责

- 实现登录页
- 实现注册页
- 实现首页页面
- 实现用户登录后的首页信息展示
- 实现首页快捷入口导航

### 6.2.2 建议负责目录

```text
lib/
├── pages/auth/
│   ├── login_page.dart
│   └── register_page.dart
├── pages/home/
│   └── home_page.dart
├── services/auth_service.dart
└── models/user_model.dart
```

### 6.2.3 详细任务

1. 登录模块

- 完成用户名密码输入表单
- 实现输入校验，例如用户名非空、密码长度校验
- 调用 `/api/auth/login`
- 登录成功后保存 token 并跳转首页
- 登录失败时显示错误提示

2. 注册模块

- 完成注册页面布局
- 支持用户名、密码、手机号、昵称等信息输入
- 调用 `/api/auth/register`
- 注册成功后跳转登录页

3. 首页模块

- 设计首页整体布局
- 展示欢迎信息、用户昵称、快捷入口
- 展示最近健康记录概览
- 展示提醒概览入口
- 展示 SOS 快捷入口按钮

4. 导航整合

- 负责将首页与其他业务模块入口打通
- 保证从首页可以进入健康记录、提醒管理、SOS 页面

### 6.2.4 交付结果

- 登录页和注册页可正常使用
- 首页可正常展示基础信息和功能入口
- 登录成功后跳转流程完整
- 首页作为项目主要演示入口可用于答辩

### 6.2.5 与其他成员的协作边界

- 成员 B 负责首页入口与页面跳转
- 健康数据入口跳转到成员 C 的页面
- 提醒和 SOS 入口跳转到成员 D 的页面
- 登录依赖成员 A 提供的网络层与 token 工具

## 6.3 成员 C：健康数据与图表负责人

### 6.3.1 主要职责

- 实现健康数据录入页面
- 实现健康记录列表页面
- 实现趋势分析页面
- 对接图表展示组件
- 调用健康记录与趋势分析相关接口

### 6.3.2 建议负责目录

```text
lib/
├── pages/records/
│   ├── record_form_page.dart
│   ├── record_list_page.dart
│   └── trend_page.dart
├── services/record_service.dart
├── services/report_service.dart
├── models/health_record_model.dart
└── widgets/charts/
```

### 6.3.3 详细任务

1. 健康数据录入

- 支持录入血压、心率、血糖、体重等健康数据
- 根据不同类型显示不同输入项
- 血压需要支持收缩压和舒张压双字段输入
- 数据提交后提示保存结果

2. 历史记录列表

- 支持按类型查询健康记录
- 支持按时间查看历史数据
- 支持列表展示测量时间、数值、状态、备注

3. 趋势图表页面

- 对接 `/api/records/trend`
- 展示血压、血糖、心率等指标折线图
- 展示平均值、最大值、最小值和异常次数
- 保证图表页面适合答辩演示，视觉清晰

4. 健康报告入口，可选增强

- 如时间允许，可增加周报页面展示
- 展示本周指标摘要与建议概览

### 6.3.4 交付结果

- 健康数据录入功能完整
- 历史记录查询可正常展示
- 趋势图表可正常渲染
- 形成健康数据模块的主要演示内容

### 6.3.5 与其他成员的协作边界

- 页面入口由成员 B 的首页统一接入
- 图表通用样式可与成员 A 协商抽成组件

## 7. 模块依赖关系

### 7.1 依赖说明

前端 4 人开发并不是完全独立，而是有明确依赖关系：

```text
成员 A 公共框架
   ↓
成员 B 登录与首页
成员 C 健康数据与图表
成员 D 提醒与 SOS
```

依赖关系说明：

- 成员 A 是基础支撑，优先级最高
- 成员 B、C、D 的页面开发依赖统一的项目骨架、路由和网络层
- 成员 B 的首页承担其他业务模块入口整合作用
- 成员 C、D 完成业务模块后需要与成员 B 联调首页跳转

## 9. 建议开发阶段安排

## 9.1 第一阶段：公共框架优先完成

时间建议：第 1 周前半段

- 成员 A 完成项目初始化
- 成员 A 提交目录结构、网络层、路由基础
- 成员 B、C、D 同步熟悉项目结构和接口文档

## 9.2 第二阶段：各模块并行开发

时间建议：第 1 周后半段到第 2 周

- 成员 B 开发登录、注册、首页
- 成员 C 开发健康记录、趋势图
- 成员 D 开发提醒、联系人、SOS

## 9.3 第三阶段：模块联调

时间建议：第 3 周

- 成员 B 整合首页入口
- 成员 C、D 接入真实接口
- 修复页面跳转、参数传递和 token 问题

## 9.4 第四阶段：测试与演示优化

时间建议：第 4 周

- 统一修复样式问题
- 统一修复接口异常提示
- 补充演示数据
- 准备答辩展示流程

## 10. 协作规范建议

### 10.1 Git 分支建议

- `main`：稳定可运行版本
- `dev`：日常集成分支
- `feature/framework`：成员 A
- `feature/auth-home`：成员 B
- `feature/health-records`：成员 C
- `feature/reminder-sos`：成员 D

### 10.2 提交规范建议

- 每完成一个小功能及时提交
- 提交信息应简洁明确
- 示例：
  - `feat: 完成登录页面表单与接口联调`
  - `feat: 完成健康记录列表页面`
  - `fix: 修复 token 失效跳转问题`

### 10.3 合并规范建议

- 先合并公共框架分支
- 业务成员每天同步 `dev` 分支最新代码
- 尽量避免多人同时修改同一页面文件
- 合并前先本地运行检查

### 10.4 UI 风格统一建议

- 统一主色调和按钮样式
- 统一页面标题和卡片风格
- 统一输入框和错误提示样式
- 保证首页、图表页、SOS 页视觉风格一致

## 12. 风险与应对措施

### 12.1 公共框架延期风险

风险说明：

- 如果成员 A 的框架搭建延后，会直接影响成员 B、C、D 的业务开发

应对措施：

- 第一个版本先完成最小可用网络层和路由
- 先保证能开发页面，后续再逐步完善公共组件

### 12.2 接口联调不及时

风险说明：

- 后端接口未完成时，前端页面可能无法联调

应对措施：

- 先使用假数据或本地 mock 数据完成页面开发
- 接口完成后再统一替换为真实请求

### 12.3 页面风格不统一

风险说明：

- 不同成员独立开发后可能出现样式差异较大问题

应对措施：

- 由成员 A 提前统一主题、颜色、按钮和卡片样式
- 第四阶段集中做一次 UI 统一整理

### 12.4 首页整合冲突

风险说明：

- 成员 B 的首页要接入成员 C 和成员 D 的页面，容易出现跳转或命名不一致

应对措施：

- 提前约定页面路由名称
- 提前明确页面参数和入口路径

## 13. 最终建议

对于 4 人前端小组而言，这种分工方式较为合理：

- 成员 A 负责“地基”，确保项目结构规范、后续开发顺畅
- 成员 B 负责“门面”，完成登录与首页，承担项目第一印象
- 成员 C 负责“核心数据展示”，体现项目的健康管理价值
- 成员 D 负责“特色功能展示”，突出提醒与紧急救援亮点

该分工方案既能体现每位成员的独立工作量，也能在答辩时清晰说明每个人负责的具体内容，适合软件工程课程项目展示与汇报。
